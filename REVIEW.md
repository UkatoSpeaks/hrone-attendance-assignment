# REVIEW.md

Defects I found in the starter `app/main.py`. Line numbers are from the starter file as it was given to me.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (33-37) | The grace check is done on whole minutes, so anything from 10:01 to 10:59 late becomes `10 > 10` and is treated as on time. | Shift 09:30, punch-in 09:40:01 returns 0. The rule says 10. | Compare seconds (`> 600`), and only then floor to minutes. |
| 2 | `compute_late_minutes` (35) | Shift start is built with `punch_in.replace(hour=..)`, so it is in whatever time zone the punch happens to be in, not IST. | On a server running in UTC, a 10:30 IST punch (05:00 UTC) is compared with 09:30 UTC and comes out as not late. | Shift start and end are built in IST from the attendance date (`shift_window`). |
| 3 | `compute_late_minutes`, `compute_overtime` | Overnight shifts are not handled. ## Looked at, and decided it was not a defect

- **`load_dotenv()` with no arguments.** It does not override variables that are already set, so real environment variables still win. That is what the environment contract asks for. I did remove the `mongodb://localhost` fallback, so a missing `MONGO_URI` fails at startup instead of quietly connecting somewhere else.
- **Plain `def` endpoints with the sync PyMongo client.** FastAPI runs them in a thread pool and `MongoClient` is thread-safe, so parallel requests are fine. I did not see a reason to move to Motor.
- **Dates stored as `"YYYY-MM-DD"` strings.** It looks odd at first, but the data model wants it, and the strings sort and compare the same way real dates do, so range queries and the index work.
- **`(punch_out - punch_in).total_seconds() / 3600`.** The formula itself is right. Only the rounding was wrong (number 5).
- **`status_code=201` on the two POSTs.** Correct as written.
- **`doc.pop("_id", None)` after `insert_one`.** Needed, because PyMongo adds `_id` to the dict it inserts. The bug was adding it back under the name `id` (number 19).
